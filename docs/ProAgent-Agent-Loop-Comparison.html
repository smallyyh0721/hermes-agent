ProAgent Agent Loop 实现与对比

本文档说明当前 ProAgent 的 agent loop 是如何工作的，并与 Hermes 原始 AIAgent.run_conversation loop 及 LangGraph 的图运行模型进行对比。本文以当前仓库代码为准。

当前实现: proagent/core/agent.py 原 Hermes loop: run_agent.py 对比对象: LangGraph

一页结论

当前 ProAgent 采用最小可控的命令式 loop：用户输入进入会话消息，调用模型，若模型返回 tool call 就执行本地域工具，再把工具结果写回消息并继续循环，直到得到最终回答或达到迭代上限。
Hermes 原始 loop 是完整产品级运行器：一个大 loop 同时承担流式输出、记忆、压缩、插件、并发工具、会话持久化、中断、委派和恢复等职责，功能强但耦合面更大。
LangGraph 把 agent 工作流建模为图：State 是共享快照，Node 执行业务步骤，Edge 决定下一步。它适合复杂、有分支、需 checkpoint 和人工介入的长期 workflow。
当前 ProAgent 的设计不是把 Hermes 全量 loop 或 LangGraph 直接搬进来，而是把多入口、多 domain pack、工具白名单、用量记录和部署形态稳定下来；复杂编排可以后续在特定 domain 内引入，而不是作为所有 agent 的基础运行成本。

当前 ProAgent Agent Loop

当前 loop 在 proagent/core/agent.py 的 ProAgent.chat() 中实现。它围绕 Message、ToolDef 和 provider adapter 工作；路由、domain pack、会话身份和接口入口由上层模块组合。

实现要点

  • chat(user_input) 先把用户输入追加为 Message(role="user")。
  • 每轮调用 _call_openai() 或 _call_anthropic()，provider 差异被限制在适配函数中。
  • 如果返回 tool_calls，先保存 assistant 消息，再逐个执行 _execute_tool()。
  • _execute_tool() 通过工具名查找 ToolDef，执行可选的 PolicyGuard 检查，再调用本地 handler。
  • 工具结果以 Message(role="tool") 写回历史，模型下一轮能读取上轮工具结果。
  • 若模型没有继续请求工具，loop 保存 assistant 最终回答并返回。

入口、路由与多 Agent 共享架构

当前项目把“agent loop”与“入口和身份”拆开。Discord、Web 和 CLI 可以共享同一套 domain pack 加载、工具注册、策略守卫、用量记录和会话标识策略。 AgentRouter 负责把入口命令映射到稳定 agent 身份，例如 sre、test、develop、aigc。

不同 agent 的差异主要来自 domain pack：系统提示词、工具集合、策略白名单、技能文件和默认运行参数不同；它们共享的是同一个小型 loop 和入口适配层。

Hermes 原始 Agent Loop

Hermes 原 loop 位于 run_agent.py，核心方法是 AIAgent.run_conversation()。 它承担了完整交互运行器职责，因此并不是简单的“模型调用 + 工具调用”循环。

与当前 ProAgent 的关系

  • ProAgent 保留了 Hermes 的核心思想：模型可以请求工具，工具结果回写消息，再继续推理。
  • ProAgent 没有继承 Hermes 大 loop 的全量运行时职责，例如流式消费者、复杂压缩、插件生命周期、并发工具池、委派任务和大型 checkpoint 管理。
  • 当前项目把这些复杂能力拆到更小的边界：入口路由、domain pack、storage、policy 和 usage 分别演进。

LangGraph 运行模型

LangGraph 官方文档把 agent workflow 建模为 graph。Graph 的核心组成是 State、Nodes 和 Edges：State 是当前快照，Node 是执行业务逻辑的函数，Edge 决定接下来执行哪个 Node。 Graph 构建完成后需要 compile，运行时可以通过 checkpointer 获得持久化和恢复能力。

因此，LangGraph 与当前 ProAgent 的区别不是“有没有工具调用”，而是控制流的表达方式不同：ProAgent 用一段直接的命令式循环表达控制流，LangGraph 用可编译图表达控制流，并把状态持久化、恢复、人工中断等能力放入图运行时。

为什么当前不直接使用 Hermes 原 loop 或 LangGraph

不直接使用 Hermes 原 loop

  • 原 loop 面向通用开发助手，依赖面和运行期状态较多；ProAgent 当前目标是 Docker 化 7/24 服务和稳定接口入口。
  • ProAgent 需要 domain pack 隔离，让 SRE、测试、开发、AIGC 等 agent 的工具权限和 prompt 可审计。
  • 小 loop 更容易确定安全边界：工具白名单、策略拒绝、结果截断和 token 用量记录都在清晰位置。

不直接使用 LangGraph

  • 当前 workflow 主要是“模型决定是否调用工具”的 ReAct 类循环，图运行时的额外抽象不是所有 domain 都需要。
  • LangGraph 的优势在复杂状态机和可恢复 workflow；这些可以作为特定 domain 的内部实现，而不必替代全局基础 loop。
  • 先保持基础 loop 小而稳定，可以降低 Discord/Web/CLI 入口同时上线的风险。
建议后续只有在某个 domain 出现固定多步流程、审批节点、失败恢复或跨 agent handoff 的明确需求时，再引入 LangGraph 作为该 domain 的 workflow engine。
